환님, 제공된 `app.py`, `receipt_pipeline.py`와 `index.html` 발췌본만을 기준으로 적대적 감사를 수행했습니다. 대상 코드 전체를 로컬에서 열거나 실행하지 않았으므로, 아래는 제공된 텍스트에서 직접 확인되는 결함과 조건부 위험입니다. 특히 `index.html`은 일부 발췌본뿐이어서 나머지 UI 구현의 결함 유무는 판정할 수 없습니다. 최근 개선 사항에 대한 주장은 코드 증거가 확인되지 않으면 검증된 사실로 취급하지 않았습니다.

## 요약: 우선순위가 높은 결함

1. **외부 LLM 출력이 스키마 검증 없이 클라이언트 응답으로 반환됩니다.** JSON 파싱 성공을 구조·타입·내용의 안전성으로 간주하며, 잘못된 형식이나 예상 밖 타입은 500 오류 또는 프론트엔드 오작동으로 이어질 수 있습니다.
2. **요청 본문 제한은 불완전합니다.** `Content-Length` 누락·비정수·음수·과다 값을 안전하게 거르지 않으며, 이미지 요청의 허용 본문 크기도 base64 문자 제한보다 큽니다. 서버 측 동시 처리 제한도 보이지 않아 느린 연결과 병렬 요청에 취약합니다.
3. **“서버 검증된 영수증”이라는 provenance 표기는 실제 출처를 보증하지 않습니다.** 서버는 클라이언트가 제출한 OCR 텍스트를 재파싱할 뿐 이미지 원본과 대조하지 않습니다. 재파싱은 클라이언트가 조작한 OCR 문구와 환자 입력을 진실한 기록으로 만들지 않습니다.
4. **개인정보 동의 모달과 실제 개인정보 보호는 제공된 발췌만으로 입증되지 않습니다.** 이미지가 외부 OCR 제공자에 전송되며 원본 OCR 텍스트도 후속 추론 요청에 포함됩니다. 코드에서 확인되는 서버 마스킹은 제한적인 정규식 방식이고, 영수증 이미지 자체나 식별자 전반을 제거하지 않습니다.
5. **“원무과 질의서 초안”이라는 고지는 모델의 실제 기능·출력 리스크를 없애지 않습니다.** 프롬프트는 급여·의학적 필요성·중복 청구와 제도별 절차를 판단하도록 요청하고, 모델이 영수증에 없는 주장이나 틀린 제도 정보를 생성하는 것을 서버가 검증하지 않습니다.
6. **I18N·A11y·UX의 완성도는 입증되지 않습니다.** 제공된 HTML 발췌에 한국어로 고정된 화면 문자열이 다수 있고, 버튼·모달·SVG 바디맵의 키보드·스크린리더 동작은 확인할 수 없습니다. 전체 언어 전환 코드가 발췌에서 빠져 있어 “완벽한 영어 I18N” 주장은 확인 불가입니다.

# 1. 해커톤 경쟁력 및 모델 아키텍처

## 확인 가능한 구현 문제

### 1.1 30B MoE 전환과 7–10초 응답은 코드만으로 검증할 수 없습니다

- `receipt_pipeline.py` 상단 주석은 “Nemotron 3 Nano 30B (MoE)”를 사용한다고 설명하고, `REASONING_MODEL`은 **8행**에서 `nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B`로 고정돼 있습니다.
- 실제 추론 요청은 **343–348행**에서 `/chat/completions`에 `timeout=120`으로 전송됩니다.
- 이 코드에는 특정 벤치마크, 반복 측정, 모델 가용성 검사 또는 7–10초 SLA 보장이 없습니다. `live_latency_ms`는 **351행**에서 단일 요청의 경과 시간을 기록할 뿐이며, 부하·콜드 스타트·네트워크 변동을 통제하지 않습니다.

따라서 “30초 지연 해소”, “7~10초 응답 달성”, “공식 엔진 전환의 실효성”은 제공된 코드만으로 입증되지 않습니다. `A3B` 표기가 활성 파라미터 수를 보장하는지, 해당 엔드포인트에서 실제로 요청되는 모델과 제공자의 배포 상태가 일치하는지도 여기서는 확인할 수 없습니다.

### 1.2 엔드포인트 URL 검증과 오류 처리에 빈틈이 있습니다

- `app.py`의 기본 URL은 **19행**에서 설정되고 `.env`의 값으로도 덮어쓸 수 있습니다(**24–27행**). 허용 호스트·스킴 제한이 없습니다.
- `_post`는 `receipt_pipeline.py` **22–29행**에서 `base_url`을 그대로 이어 붙여 요청합니다. 설정 파일이 신뢰 경계 밖에서 변경될 수 있다면 잘못된 호스트로 키를 전송하는 위험이 생깁니다. `.env`의 실제 파일 권한 및 편집 권한은 확인하지 못했으므로 공격 가능성을 단정할 수는 없습니다.
- OCR 기본 모델 호출과 fallback은 각각 `receipt_pipeline.py` **45–56행**, **68–79행**에서 예외를 잡고 로그를 남깁니다. 로그에는 예외 문자열이 포함됩니다. 공급자 예외 문자열에 URL·요청 세부 정보가 포함되는지는 구현·라이브러리에 따라 달라 여기서는 미확인입니다.
- 추론 단계는 **343–348행**에서 OCR과 달리 fallback이 없고, `app.py` **85–88행**에서 `HTTPError`를 502로 변환합니다. HTTP 외 연결 오류·타임아웃은 **92–97행**의 포괄 예외 처리로 500이 됩니다. 사용자에게는 내부 예외 텍스트 일부가 그대로 반환됩니다.
- OCR 요청 타임아웃은 주 모델 90초, fallback 120초(각각 **53행**, **76행**)이고 추론 요청은 120초(**348행**)입니다. 한 요청에서 기본 OCR과 fallback이 연속 실행될 수 있으므로, 처리 시간이 120초를 훨씬 넘을 수 있습니다. 서버 자체의 요청 데드라인이나 취소 전파는 보이지 않습니다.

이 구조는 경쟁 시연에서도 지연 편차·실패율·공급자 오류 대응을 예측하기 어렵게 합니다. **‘모델에 연결된다’와 ‘해커톤 환경에서 안정적으로 응답한다’는 서로 다른 증거가 필요합니다.**

### 1.3 OCR fallback 조건은 문서 품질에 대한 신뢰성 있는 판정이 아닙니다

`receipt_pipeline.py` **60–62행**은 반복 줄 수, 총 줄 수, 일부 한국어 키워드 존재 여부로 fallback을 결정합니다.

- 한국어 표가 50줄 이상이면 fallback이 불필요하다고 간주할 수 있지만, 줄 수가 많다는 사실은 정확도를 보증하지 않습니다.
- 3줄 이상이고 반복이 적은 잘못된 OCR 결과는 통과할 수 있습니다.
- 대만·미국 문서에 같은 품질 감지 기준이 적용되지 않습니다.
- fallback 결과는 이전 결과와 대조·결합하거나 정확도 점수로 검증하지 않고, 결과가 비어 있지 않으면 통째로 덮어씁니다(**73–78행**).
- “환각/표 품질 저하 감지” 주석(**59행**)과 실제 품질 판정 사이에 신뢰 가능한 평가 로직이 없습니다.

따라서 “복잡한 표에서 graceful fallback”은 예외 후 재시도 경로가 있다는 뜻일 뿐, 복구된 OCR의 정확성이나 우월성을 의미하지 않습니다.

### 1.4 프롬프트 지시는 출력 제약이 아닙니다

- OCR 프롬프트는 `receipt_pipeline.py` **12–20행**에서 정확한 전사와 평문 출력을 요청하지만, 결과를 원본과 대조하는 검증은 없습니다.
- 추론 프롬프트는 JSON만 출력하라고 지시합니다(**269–277행**). 실제 JSON 추출은 **318–330행**에서 `{`부터 마지막 `}`까지 잘라 파싱하고, 실패하면 임의의 닫는 문자를 덧붙여 재시도합니다. 이는 JSON **추출**이지 고정 스키마 검증이 아닙니다.
- 파싱 결과는 **343–353행**에서 딕셔너리라고 가정해 바로 항목을 추가합니다. JSON이 배열, `null`, 문자열이면 이후 조작에서 실패할 수 있습니다.
- `document_type`, `target_item`, `reasoning`, `questions`, `inquiry_letter`, `inquiry_letter_local`, `ocr_uncertainties`의 필수 여부·타입·길이·허용값을 검사하는 코드가 제공된 구현에는 없습니다.
- `"target_item"`은 “정확한 청구 항목을 보존”하라는 프롬프트 지시일 뿐(**264–266행**), 서버가 파서 결과와 비교해 일치 여부를 확인하지 않습니다.

**판정:** 프롬프트는 모델에 대한 요청이지 보안·의료·재정상 결과의 제약 조건이 아닙니다. 출력 스키마 강제와 증거 일치 검증은 코드에서 확인되지 않습니다.

# 2. 서버 사이드 데이터 무결성 및 보안

## 2.1 재파싱은 위조 방지가 아니라 클라이언트 JSON 필드 하나를 무시하는 조치입니다

- `/api/audit-bill` 처리에서 입력은 **app.py 51–52행**, `receipt`와 `receipt.lines`는 **54–55행**에서 가져옵니다.
- `raw_lines`가 빈지 여부만 검사합니다(**55–58행**).
- 서버는 받은 텍스트를 필터링한 뒤 `rp.parse_receipt(safe_lines)`를 호출합니다(**77–79행**). 클라이언트가 제출한 `receipt.parsed` 필드는 사용하지 않는다는 점은 확인됩니다.
- 그러나 `safe_lines` 자체가 클라이언트가 제출한 값입니다. 서버가 업로드 이미지를 보관·재OCR하거나 서명된 OCR 결과와 대조하지 않습니다. `/api/scan-receipt`에서 받은 OCR 결과도 서버 세션에 묶이거나 서명되는 구현이 보이지 않습니다.

따라서 공격자는 이미지 업로드 단계를 거치지 않고도 `/api/audit-bill`에 임의의 `lines`를 직접 제출해 파서 결과와 추론 입력을 구성할 수 있습니다. 재파싱은 **클라이언트가 보낸 `parsed` 객체의 조작**을 막을 뿐, **OCR 텍스트의 조작**이나 **영수증 내용의 진위**를 막지 않습니다.

특히 provenance 문자열 `"server_verified"`(**app.py 79행**)은 코드가 실제로 검증하는 범위를 넘어섭니다. 확인되는 사실은 “서버가 클라이언트 제공 줄을 다시 파싱했다”는 것뿐입니다. 이 라벨은 후속 코드나 UI에서 신뢰 표시로 사용될 경우 잘못된 출처 보증이 됩니다.

### 2.2 환자 입력도 신뢰 가능한 임상·기기 데이터가 아닙니다

- `condition`과 `pain_regions`는 요청 본문에서 그대로 문자열로 가져와 길이만 자릅니다(**app.py 68–69행**).
- `vas`는 정수 변환 실패 시 0, 성공 시 0–10 범위로 클램프됩니다(**60–67행**). 이 값은 범위만 제한하고 환자의 실제 응답·작성 시점·동일성은 확인하지 않습니다.
- `pins`는 정수 변환 후 음수만 0으로 제한하며 상한이 없습니다(**64–67행**). 값이 모델 프롬프트에 그대로 들어갑니다(`receipt_pipeline.py` **290행**). 이 필드가 실제 좌표 목록이 아니라 단순 숫자라면 신체 부위의 세부 위치를 검증할 수 없습니다.
- `wearable`은 클라이언트 값에서 걸음 수와 각성 시간을 받습니다(**app.py 70–73행**). 정수형·합리적 상한·데이터 출처를 확인하지 않습니다. 입력 필터는 `isdigit()` 여부뿐입니다. 매우 큰 숫자 문자열에 대한 제한이 없습니다.
- `drop_pct`는 기준 걸음 수가 0이 아닐 때 계산합니다(**app.py 71행**). 비정상적으로 큰 값도 그대로 모델 입력이 될 수 있습니다.

화면에서 환자가 입력한 값과 실제로 검증된 의료 기록·웨어러블 센서 데이터를 구분해야 합니다. 현재 코드에서 확인되는 것은 사용자가 보낸 값의 부분적 정리뿐입니다.

### 2.3 요청 본문 크기 제한이 일관되지 않고 파서 오류를 충분히 다루지 않습니다

- `_read_json`은 `Content-Length`를 `int()`로 변환합니다(**app.py 43행**). 헤더 누락은 0으로 처리하지만, 비정수 값이면 `ValueError`가 발생합니다. `do_POST`의 전체 `try` 안에서 잡히므로 응답은 500이며 잘못된 요청으로 분류되지 않습니다.
- 음수 길이는 제한에 걸리지 않고, `rfile.read(length)`에 음수가 들어갈 수 있습니다(**44행**). 이때 동작은 요청의 실제 framing과 서버 라이브러리 동작에 의존합니다. 명시적 거부가 없습니다.
- 허용량 초과만 `OverflowError`로 413 처리합니다(**app.py 42–45행**, **88–89행**). `Content-Length`가 없는 청크 전송 요청의 처리·거부 정책은 구현에서 확인되지 않습니다.
- `/api/scan-receipt` 본문 상한은 `MAX_IMAGE_CHARS + 10_000`(**app.py 50행**)이지만 `MAX_IMAGE_CHARS`는 base64 이미지 문자열 제한(**receipt_pipeline.py 10행**)입니다. JSON 필드·data URL 접두부 등 부가 크기를 더하는 설계는 있으나, 이 둘이 정확히 조정되는지 검증되지 않았습니다.
- `_read_json`은 본문을 메모리에 한 번 읽고 UTF-8로 디코딩한 뒤 JSON으로 파싱합니다(**app.py 44–45행**). 제한 내 요청도 여러 스레드에서 동시에 도착하면 메모리·CPU를 소모할 수 있습니다.

`ThreadingMixIn` 서버는 동시 연결마다 스레드를 사용하고, 제공된 코드에는 스레드 풀 크기 제한·요청 속도 제한·동시 외부 호출 제한이 없습니다(**app.py 102–105행**). 각 스캔은 최대 두 번의 외부 OCR 호출을 할 수 있고, 감사는 외부 모델 호출을 수행합니다. 따라서 느린 요청과 병렬 요청을 이용한 가용성 저하 위험이 있습니다.

### 2.4 OCR 데이터 URL과 이미지 처리 방어가 부족합니다

- `ocr_image`는 문자열인지와 `data:image/` 접두어인지, 문자 수만 확인합니다(**receipt_pipeline.py 88–92행**). 실제 MIME 유형·인코딩·압축 해제 크기·픽셀 수 상한을 먼저 검증하지 않습니다.
- `_prepare_image`는 base64 디코딩 및 PIL 이미지 디코딩을 시도하고 실패하면 **원본 data URL을 그대로 반환합니다**(**receipt_pipeline.py 31–43행**). 즉, 디코딩 실패가 거부로 이어지지 않습니다.
- 이미지가 `Image.open(...).convert("RGB")`에서 전부 메모리로 디코딩되며, 픽셀 폭·높이에 대한 명시적 최대치가 없습니다(**receipt_pipeline.py 34–40행**). 압축 폭탄류 입력에 대한 별도 방어가 확인되지 않습니다. PIL 자체의 경고·오류 설정 상태는 미확인입니다.
- OCR 응답에서 구조 접근은 `data["choices"][0]["message"]`에 의존합니다(**receipt_pipeline.py 51행**, **73행**). 응답 구조가 다르면 예외 처리로 빠질 수 있지만, 외부 응답 스키마 검증은 없습니다.

### 2.5 예외와 로그 처리로 내부 정보가 노출될 수 있습니다

- 일반 예외 메시지는 최대 300자로 잘라 클라이언트 응답에 직접 담깁니다(**app.py 92–97행**).
- `HTTPError`의 본문은 로그에 최대 300자 출력됩니다(**app.py 90–91행**). 공급자가 요청 내용, 상관관계 ID, 내부 세부 정보를 오류 본문에 포함하는지 확인되지 않았습니다.
- 예외 처리에서 `traceback.print_exc()`를 호출합니다(**app.py 93–96행**). 공개 인터넷 서비스가 아니라 `127.0.0.1`에 바인딩하는 점은 공격 노출면을 제한하지만(**app.py 13행**, **107–109행**), 배포 토폴로지·리버스 프록시 설정은 제공되지 않아 실제 외부 접근 여부를 판단할 수 없습니다.
- 경로 접근에 대해서는 화이트리스트와 차단 로직이 있습니다(**app.py 32–40행**). 다만 `self.path == "/favicon.ico"` 비교(**app.py 47행**)는 쿼리 문자열이 붙은 요청을 다르게 처리할 수 있습니다. 이것이 보안 취약점이라는 점까지는 입증되지 않으나, 경로 정규화 기준이 GET·화이트리스트 사이에서 일관적인지 테스트가 없습니다.
- CSP, CORS, CSRF 방어, 보안 응답 헤더는 제공된 서버 코드에서 확인되지 않습니다. 브라우저 데모의 실사용 배포 조건이 알려지지 않았으므로 구성 결함의 실제 노출도는 미확인입니다.

# 3. 헬스케어 규제 및 개인정보(PII)

## 3.1 외부 처리의 실제 경로는 코드에 있고, 동의 절차는 발췌로 확인되지 않습니다

확인되는 데이터 흐름은 다음과 같습니다.

1. 클라이언트가 `/api/scan-receipt`에 이미지 데이터를 보냅니다(`app.py` **50행**).
2. 서버는 이미지를 가공한 뒤 OCR 모델에 `image_url` 데이터로 전달합니다(`receipt_pipeline.py` **31–43행**, **45–56행**). 현재 선택된 엔드포인트는 설정값에 따릅니다(`app.py` **19–27행**, `receipt_pipeline.py` **9행**).
3. OCR 텍스트는 `/api/scan-receipt` 응답으로 클라이언트에 반환됩니다(`app.py` **53–58행**).
4. 감사 요청 시 클라이언트가 영수증 줄과 환자 입력을 다시 전송하고(`app.py` **54–79행**), 서버는 제한적인 마스킹을 거친 OCR 텍스트와 환자·웨어러블 값을 추론 모델에 전달합니다(`receipt_pipeline.py` **283–316행**, **343–348행**).

즉, **이미지 OCR과 추론 모두 외부 API 호출을 통해 이루어지는 구조**입니다. 단, 코드만으로 API 운영자, 리전, 데이터 보존·학습 정책, 전송 암호화 설정, 데이터 처리 계약, 하위 처리자, 삭제 보장, 접근 통제 등을 확인할 수 없습니다. 따라서 특정 사업자의 실제 처리 조건이나 법규 준수 여부를 단정하지 않습니다.

`index.html` 발췌에는 동의 모달이 나오지 않습니다. 그러나 발췌가 중간에서 끝나므로 파일 전체에 모달이 없다고 판단할 수는 없습니다. 또한 모달이 있더라도 실제 동의의 적법성과 충분성은 별도 문제입니다. 확인하려면 적어도 전송 대상, 전송 항목, 목적, 처리·보관 기간, 제공자 역할, 선택 거부 시 기능, 철회 방법, 국내외 이전 여부, 거부 후 이미지·텍스트의 보관 여부와 실제 서버 동작을 대조해야 합니다. 현재는 이 항목의 구현을 입증할 코드가 제공되지 않았습니다.

## 3.2 현재 서버 마스킹은 개인정보 비식별 처리로 보기 어렵습니다

- `_mask_identifiers`는 `_ID_KW` 또는 `_BIRTH_KW`가 매칭되는 줄에서만 숫자 패턴을 치환합니다(`receipt_pipeline.py` **214–219행**).
- `_ID_KW`는 특정 키워드 목록에 기대고 있습니다(**38–39행**). 이름, 상세 주소, 전혀 예상하지 못한 식별자 형식, 키워드와 분리된 전화번호 등은 그대로 남을 수 있습니다.
- 대체 정규식은 `[A-Z]?\d[\d*\-]{2,}`(**218행**)으로 제한돼 있습니다. 그 자체로 한글·영문 이름이나 주소를 가리지 않습니다.
- 프롬프트에서 개인정보를 복사하지 말라고 요청하지만(**260–263행**), OCR 원문은 모델 입력에 포함되고 모델 지시는 기술적 제거가 아닙니다.
- **중요:** `/api/scan-receipt`는 `lines`를 그대로 클라이언트로 반환합니다(`app.py` **54–58행**). 이 코드에는 OCR 응답의 식별자 제거가 없습니다. 추론 시점의 마스킹이 스캔 응답·브라우저 상태·클라이언트 저장을 소급해 정화하지 않습니다.
- `_prepare_image`는 원본 이미지의 일부가 포함된 전체 문서를 외부 OCR 호출에 전달합니다(`receipt_pipeline.py` **31–43행**, **45–56행**). OCR 전 이미지상의 이름·번호·주소를 가리는 로직은 보이지 않습니다.

따라서 “개인정보 동의 모달”이 있더라도 그것만으로 개인정보 최소화·비식별화가 이루어졌다고 볼 수 없습니다.

## 3.3 “원무과 질의서 초안”이라는 문구가 규제 경계를 자동으로 해결하지 않습니다

프롬프트는 진단·불법 단정을 금지합니다(**receipt_pipeline.py` 256–260행**). 하지만 동시에 모델에 다음을 요청합니다.

다만 “초안”, “의료적 진단이나 법률적 판정이 아님”이라는 UI 문구는 **실제 기능의 성격, 마케팅 표현, 사용자가 결과를 신뢰해 행동할 가능성**을 무효화하지 않습니다. 또한 모델이 틀린 보험·청구 규칙을 적용하거나, 사실과 무관한 항목을 의심 대상으로 고르더라도 이를 탐지하는 로직은 제공된 코드에서 확인되지 않습니다.

# 4. 프론트엔드 UI/UX 및 I18N·A11y

## 4.1 영어 I18N “완벽” 주장은 발췌본만으로 검증할 수 없고, 고정 문자열은 확인됩니다

제공된 HTML에는 한국어로 고정된 문자열이 다수 남아 있습니다. 예를 들면 다음과 같습니다.

- `<html lang="ko">`(**1행**)은 언어를 전환하더라도 문서 언어 속성을 바꾸지 않으면 보조 기술·브라우저에 한국어 페이지라고 계속 알립니다.
- 머리글 제목은 한국어 고정입니다(예: **145–147행** 주변의 “페인프리”).
- 섹션 제목·보조 문구 및 환자 입력 레이블이 HTML에 직접 들어 있습니다(발췌의 섹션 1·2·3).
- `ocrRaw` 설명, `details`의 OCR 보기 문자열, 업로드 샘플 출처 문구도 정적 한국어입니다.
- 화면 설명은 OCR, parsing, reasoning 단계를 사용자에게 표시하지만, 이에 대응하는 영문 문자열이 이 발췌에는 없습니다.

영문 UI 문자열 생성, `switchLanguage`, 상세 모달·저널·리포트의 번역 사전은 발췌에서 확인되지 않습니다. 파일 후반에 존재할 수 있으므로 전체 구현의 실패라고 단정하지는 않습니다. 다만 이 자료로는 “주치의 리포트, 바디맵, 저널 상세 모달 전체의 완벽한 영어 I18N”을 검증할 수 없습니다.

또한 서버는 언어 선택을 정확히 `"EN"`과 일치하는 경우에만 영어로 설정하고, 그 외는 한국어로 전달합니다(`app.py` **80행**). 따라서 프론트엔드가 `en`, `en-US`, 공백 포함 값 등을 보낼 경우 서버 출력 언어는 한국어가 됩니다. 실제 프론트엔드 요청 값은 발췌에서 확인되지 않습니다.

## 4.2 접근성 위험

- 화면에 버튼 요소가 사용된 것은 일부 확인되지만(**예: index.html 버튼 다수**), 일반적인 버튼에 명시적인 `aria-label`, `aria-pressed`, 초점 표시, 키보드 사용 설명이 있는지는 보이지 않습니다.
- VAS 슬라이더는 `<input type="range">`로 구현되어 있지만(**발췌의 `vasSlider`**), 접근 가능한 이름·`aria-valuetext`·색상 이외의 통증 수준 표현은 확인되지 않습니다. 색상과 숫자만으로 상태를 전달하면 저시력·색각 사용자에게 정보가 손실될 수 있습니다.
- 모달이 여러 개라는 것은 UI 발췌에서 확인되지만, 닫기 시 초점 복귀, `role="dialog"`, `aria-modal`, 포커스 가두기, `Escape` 처리, 제목 연결 여부는 제공된 모달 코드가 잘려 있어 확인할 수 없습니다.
- 바디맵이 SVG 상의 정밀 핀을 포함할 것이라는 UI 설명은 보이지만, 스크린리더에 대한 비텍스트 대체, 키보드로 핀 생성·선택, 위치를 텍스트로 확인·수정하는 대체 경로는 확인되지 않습니다.
- 작은 텍스트 사용이 광범위합니다. 예를 들어 환자 기록·상태·도움말에 `text-[9px]` 및 `text-[10px]`이 여러 곳에 사용됩니다. 화면 폭 420px을 기준으로 설계한 컨테이너(**index.html의 `#app-container`, 발췌**)와 결합해 화면 확대 시 줄바꿈·레이아웃 변화가 전체적으로 적절한지는 시험되지 않았습니다.

이는 코드 발췌로 확인되는 검수 공백이며, 실제 키보드·스크린리더·확대 사용에서 실패했다는 테스트 결과는 아닙니다.

## 4.3 동의 UX는 모달 표시 여부보다 실제 데이터 흐름과 연결돼야 합니다

파일 발췌에는 파일 입력 요소와 `handleFileUpload(event)` 호출이 있습니다(SECTION 2). 동의 모달이 파일 선택 이전에 반드시 실행되는지, 모달을 거부했을 때 업로드 및 샘플 영수증 처리가 차단되는지, 이미 선택된 파일이 동의 거부 후 제거되는지, 감사 요청 직전에 서버에서도 동의 상태를 확인하는지는 알 수 없습니다.

따라서 JIT 동의 모달 구현 주장은 **제공된 코드에서 검증되지 않았습니다.** 클라이언트 UI만으로 동의 여부를 표시하더라도 서버는 동의 상태를 전달·검증하지 않으므로, 서버가 동의 조건을 강제한다는 근거는 없습니다. 실제 적용에서 어떤 동의 증적이 법적으로 필요한지는 관할과 사용 방식에 따라 별도 검토가 필요합니다.

## 4.4 바디맵·저널·리포트의 구조적 위험

- `index.html`은 환자의 상태, 통증, 웨어러블 값, 영수증 내용을 하나의 흐름으로 수집하는 UI를 보여 줍니다. 의료 민감정보를 브라우저 로컬 스토리지나 서버에 저장하는지, 저장 기간·삭제·내보내기 동작은 발췌에서 확인되지 않습니다.
- 저널은 “최근 기록 일지” 및 저장 버튼을 제공하지만, 저장 위치와 접근 제어는 확인되지 않습니다. “기록 일지에 저장”이 영속 저장을 의미한다면 사용자에게 저장 범위와 삭제 방법을 명확히 보여야 하나, 해당 동작은 확인할 수 없습니다.
- 주치의 1페이지 리포트의 인쇄 스타일은 **CSS `@media print`**에서 모달을 표시하도록 합니다. 그러나 인쇄 시 민감정보가 어떤 항목까지 포함되는지, 화면에 숨겨진 개인정보가 함께 출력되는지, 인쇄용 언어가 현재 선택 언어를 따르는지는 구현 발췌가 충분하지 않습니다.
- 사용자에게 “1페이지”를 약속하는 UI 주장은 있지만, 콘텐츠 길이·폰트 크기·다국어 문장 확장에 대해 실제 한 페이지 제한을 보장하는 로직은 보이지 않습니다. 긴 영어 번역이나 많은 저널·핀·OCR 결과에서 페이지가 넘칠 가능성은 검증되지 않았습니다.
- `maximum-scale=5.0, user-scalable=yes`(**index.html 4행**)는 확대 허용 설정이지만, 확대 중 모달·바디맵·고정 하단 내비게이션이 가시성 및 조작성을 유지한다는 보장은 아닙니다. 실제 브라우저 시험이 필요합니다.

## 결론

현재 제공된 코드에서 가장 큰 위험은 **“서버 재파싱”과 “서버 검증”을 혼동하는 것**, **외부 모델 출력을 신뢰 경계 없이 응답으로 내보내는 것**, **환자·영수증 데이터가 외부 모델로 전달되는 범위에 대해 실제 처리 통제와 검증 근거가 제시되지 않은 것**입니다. 특히 `server_verified` provenance 값, “실제 영수증에 근거한” 결과로 오해될 수 있는 사용자 표시, 그리고 임상·급여 판단을 연상시키는 기능 설명은 서로 결합돼 결과 신뢰를 과도하게 높일 수 있습니다.

규제 적용 여부·사업자 데이터 처리 조건·배포 환경·전체 프론트엔드 동작은 제공 자료로 확인할 수 없으므로 확정적 법률 결론은 내리지 않습니다. 다만 위 코드만으로는 개인정보 최소화, 출력 신뢰성, 요청 남용 방어, 동의의 실제 강제, 다국어·접근성의 완성도를 입증할 수 없습니다.
