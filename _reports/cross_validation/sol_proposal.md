환님, **환님의 반론이 타당합니다. 현재 용도가 ‘환자 본인의 원무과 문의용 초안’이라면, 클라이언트 `parsed` 조작 가능성을 곧바로 P0로 분류하는 것은 과도합니다.** 가장 현실적인 개선은 DB나 서버 세션을 추가하는 것이 아니라, **추론 직전에 서버에서 다시 파싱하고, 개인정보 외부 전송 전 동의를 확인하며, 모델 크기보다 실제 품질·속도 측정으로 모델을 선택하는 것**입니다.

아래는 파일을 수정하지 않은 **텍스트 개선 제안서**입니다.

> **검토 범위와 한계**
> - 근거는 환님이 제공하신 `app.py`, `receipt_pipeline.py`, `index.html` 발췌입니다. 실제 로컬 파일·운영지침·프로젝트 지침은 이 환경에서 열람하지 못했습니다.
> - 실행, API 호출, 최신 모델 목록, 공급자 계약, 해커톤 공식 규칙, 현행 법령 개정 상태는 확인하지 않았습니다.
> - 따라서 실제 동작 PASS, 규제 준수 완료, 특정 모델의 제공 여부 또는 우승 확률을 확정하지 않습니다.
> - 실제 파일 행 번호를 확인하지 못했으므로, 아래 증거는 **함수명과 정확한 코드 행**으로 식별합니다. 임의의 파일 행 번호를 만들지 않습니다.

# 2. 질문 1 — 클라이언트 파싱 조작 리스크 재평가

## 2.1 환님의 지적이 타당한 이유

현재 UI는 결과를 다음처럼 설명합니다.

**증거 Q1-UI — `index.html`, `auditDisclaimerText`**
```html
* 본 문서는 의료적 진단이나 법률적 판정이 아니며, 환자가 병원 원무과에 확인을 요청할 때 참고하는 질의서 초안입니다.
```

이 범위에서는:

- 앱 출력이 병원 EMR이나 청구 원장을 직접 변경하지 않습니다.
- 지급·환급·보험 심사를 자동 승인하는 코드가 제공되지 않았습니다.
- 병원이 자체 원본으로 사실관계를 확인할 수 있다는 환님의 운영 전제는 합리적입니다.
- 환자가 자신의 문의 초안을 조작할 유인은 금융 거래 시스템의 조작 유인보다 작습니다.

다만 **모든 병원에 해당 원본이 존재하고 항상 대조한다는 점은 이번 자료로 확인한 사실이 아니라 운영 가정**입니다.

따라서 재평가는 다음과 같습니다.

> **현 제공 범위에서는 P0를 철회하는 것이 타당합니다. 개인용 문의 초안의 데이터 일관성 문제로 분류하고, 저비용으로 해결합니다.**

P0에 가까워지는 것은 이 결과를 보험금 지급, 자동 환급, 공식 증빙, EMR 쓰기 등에 신뢰하여 사용하는 경우입니다. 현재 자료에는 그러한 기능이 없습니다.

## 2.2 악의적 위조보다 더 현실적인 문제

**증거 Q1-A — `app.py`, `do_POST`, 감사 분기**
```python
safe_receipt = {"lines": [str(x)[:300] for x in receipt.get("lines", [])][:200],
                "parsed": receipt.get("parsed") or {}}
result = rp.reason(NEBIUS_BASE_URL, NEBIUS_API_KEY, "EN" if body.get("ui_lang") == "EN" else "KR",
                   patient, wearable, safe_receipt)
```

서버는 `lines`의 길이를 제한하지만, `parsed`는 클라이언트 값을 그대로 받아 추론에 넣습니다.

이로 인해 다음 문제가 가능합니다.

1. 다른 영수증의 OCR과 파싱 결과가 섞이는 UI 상태 오류.
2. 이전 파서 버전 결과를 새 서버로 보내는 버전 불일치.
3. `parsed.items`에 잘못된 자료형이 들어가 추론 준비 단계가 실패하는 경우.
4. OCR에는 없는 항목을 모델이 실제 영수증 항목으로 취급하는 경우.

**증거 Q1-B — `receipt_pipeline.py`, `build_reasoning_messages`, 시스템 지시**
```python
"Only cite items that actually appear in the OCR text or parsed items. "
```

현재 지시는 OCR 또는 `parsed` 중 **한쪽에만 있어도** 인용을 허용합니다. 따라서 서버 재파싱은 위조 방지보다 **출력 근거의 일관성을 확보하는 개선**으로 설명하는 편이 정확합니다.

## 2.3 가장 가벼운 권장 파이프라인

```text
브라우저
  ├─ 전송 전 동의
  ├─ 이미지 자르기·가리기 및 전송본 확인
  └─ 이미지 → 서버

서버 /scan-receipt
  ├─ 동의·이미지 크기·자료형 검증
  ├─ OCR 호출
  ├─ Python 파싱
  └─ OCR + 파싱 결과 반환

브라우저
  └─ OCR 확인/수정 → 문의 초안 생성 요청

서버 /audit-bill
  ├─ 동의·요청 자료형 검증
  ├─ OCR lines 정규화
  ├─ Python 재파싱: 클라이언트 parsed는 사용하지 않음
  ├─ 추론용 최소 항목만 구성
  ├─ 모델 호출
  ├─ 결과 스키마·항목 근거 검증
  └─ 문의 초안 반환
```

**추가 DB·로그인·영수증 세션 저장은 필요하지 않습니다.**

### 텍스트 변경 초안

```python
# 제안용 코드: 적용·실행하지 않음
lines = validate_receipt_lines(receipt.get("lines"))
parsed = rp.parse_receipt(lines)

safe_receipt = {
    "lines": lines,
    "parsed": parsed,
}
```

`validate_receipt_lines`에는 다음 조건을 둡니다.

- 배열인지 확인.
- 각 원소는 문자열만 허용.
- 줄 수, 줄당 길이, 전체 문자 수 제한.
- 비정상 입력은 조용히 변환하기보다 400으로 거절.

**보장 범위:** 이 설계는 `lines`와 `parsed`의 불일치를 없애지만, `lines` 자체가 서버 OCR 결과임을 인증하지는 않습니다. 그러나 환자 문의용 초안에는 이 정도가 현실적인 기본선입니다.

### 원본 OCR 출처까지 필요할 때만: 서명 봉투

나중에 “서버가 인식한 결과”임을 구별해야 한다면, DB 대신 HMAC 서명 봉투를 사용할 수 있습니다.

```text
payload = {OCR lines, 발급 시각, 만료 시각, 파서 버전}
signature = HMAC(server_secret, canonical_payload)
```

감사 요청 시 서명을 검증하고 서버에서 재파싱합니다.

주의사항:

- 서명은 암호화가 아닙니다.
- 원본 사진의 진실성이나 환자의 신원을 증명하지 않습니다.
- OCR 수정 시에는 ‘환자 수정본’으로 구분해야 합니다.
- 재사용 자체를 막으려면 별도 상태 관리가 필요합니다.

**현재 MVP에는 서명조차 필수가 아닙니다. 먼저 재파싱만 적용하는 것을 권고합니다.**

## 2.4 더 중요한 신뢰성 개선

**증거 Q1-C — `receipt_pipeline.py`, 한국 표 형식 처리**
```python
is_noncovered = len(nums) >= 3 and val_floats[-1] > 0
main_amt = val_floats[-1] if is_noncovered else val_floats[0]
```

숫자가 3개 이상이고 마지막 값이 양수라는 조건만으로 비급여를 추정합니다. 표 열의 의미를 확인하지 않으므로, 정상 환자가 사용해도 잘못 분류될 수 있습니다.

**증거 Q1-D — 같은 파일, `detect_currency`**
```python
if re.search(r"[\u4e00-\u9fff]", blob):
    return "TWD"
```

한자가 있다는 이유만으로 TWD를 확정합니다. 중국·일본 자료에도 적용될 수 있으므로 국가와 통화 추정을 분리해야 합니다.

권고:

- 표 머리글을 확인하지 못하면 `noncovered=None`.
- 통화·국가가 모호하면 사용자 확인.
- `총진료비`, `환자 부담액`, `납부액`을 별도 필드로 구분.
- 증거 없는 급여·비급여 판정 대신 “이 항목의 구분을 확인해 주세요”라고 질문.

**악의적 조작보다 정상 입력의 오해석을 먼저 줄이는 것이 실제 사용자 가치가 큽니다.**

# 3. 질문 2 — 명시적 동의의 UI/UX와 백엔드 설계

## 3.1 답변: 동의만으로 완전한 해결은 아닙니다

환님 말씀처럼 **명시적 동의는 가장 중요한 출발점**입니다. 다만 동의가 다음을 자동으로 해결하지는 않습니다.

- 어떤 사업자가 어떤 국가에서 데이터를 처리하는지.
- 공급자의 저장 기간과 학습 사용 여부.
- 민감정보를 처리할 적법한 근거.
- 필요한 처리위탁·제3자 제공·국외 이전 절차.
- 보안 조치, 권리 행사, 삭제·철회 절차.
- HIPAA 적용 시 필요한 공급자 계약.

따라서 **“동의 팝업으로 HIPAA/GDPR/PIPA 완벽 PASS”라는 표현은 사용하면 안 됩니다.** 심사 기준 자체도 확인되지 않았으므로 무감점은 보장할 수 없습니다.

## 3.2 현재 코드의 전송 위치와 마스킹 한계

**증거 Q2-A — `receipt_pipeline.py`, `ocr_image`, 기본 OCR 요청**
```python
{"type": "image_url", "image_url": {"url": optimized_url}}
```

원본에서 생성한 이미지를 외부 API에 전달합니다.

**증거 Q2-B — `_prepare_image`**
```python
im = Image.open(io.BytesIO(raw)).convert("RGB")
im.thumbnail((2400, 2400), Image.LANCZOS)
```

이미지 형식·크기를 조정할 뿐 개인정보를 가리지 않습니다.

**증거 Q2-C — `_mask_identifiers`**
```python
if _ID_KW.search(ln) or _BIRTH_KW.search(ln):
    ln = re.sub(r"[A-Z]?\d[\d*\-]{2,}", "***", ln)
```

이 마스킹은 OCR 이후 일부 숫자 식별자를 처리합니다. 이미지 단계 외부 전송을 방지하지 않으며, 이름·주소·라벨 없는 식별자를 포괄적으로 제거하지 않습니다.

또한 `parsed` 필드는 별도 경로로 프롬프트에 삽입됩니다. 원문 일부를 마스킹했다고 전체 입력이 비식별화됐다고 주장할 수 없습니다.

**동의 확인 시점은 ‘감사 실행’이 아니라 최초 OCR 호출 이전이어야 합니다.**

## 3.3 권장 UX

### 첫 화면

짧게 안내합니다.

> 통증 기록은 외부 AI 분석 없이도 입력할 수 있습니다. 영수증 인식과 문의 초안 생성에는 외부 AI 서비스로 선택한 자료가 전송됩니다.

실제 로컬 기록 기능의 동작은 전체 JavaScript를 확인한 뒤 확정해야 합니다.

### 사진 선택 후, 최초 전송 전

사진을 선택했다고 즉시 전송하지 않습니다.

1. 전송할 사진 미리보기.
2. 이름·환자번호·전화번호·주소·QR/바코드를 가리는 도구.
3. 실제 수신 서비스, 처리 국가, 목적, 자료 항목, 보관 조건 표시.
4. 필요한 동의를 구분해 선택.
5. **“동의하고 이 사진 전송”** 버튼.

권장 구조는 다음과 같습니다.

| 항목 | 방식 |
|---|---|
| 개인정보 수집·이용 안내/동의 | 적용 법적 근거에 맞춰 별도 고지 |
| 건강정보 등 민감정보 처리 | 한국 동의 기반이면 일반 개인정보 동의와 구분 |
| 외부 처리 및 국외 이전 | 법적 관계와 이전 근거에 맞춰 별도 안내·필요한 동의 |
| 분석 개선·연구·학습 목적 | 선택, 기본 해제, MVP에서는 수집하지 않는 편 권장 |

모든 항목을 하나의 “서비스 이용에 동의합니다”에 묶지 않습니다. 다만 **모든 법역에서 동일한 체크박스 개수가 법적으로 필수인 것은 아닙니다.** 실제 처리 구조에 맞춰 구성해야 합니다.

### 실전 문구 초안

> **외부 AI 분석 안내**  
> 선택한 영수증 이미지와 인식된 진료비 항목을 영수증 인식 및 문의 초안 생성 목적으로 외부 AI 처리 서비스에 전송합니다. 통증·질환·활동량 정보는 해당 기능에서 선택한 경우에만 함께 전송합니다.  
> 수신 사업자: `[확인된 법인명]`  
> 처리 국가/지역: `[확인된 지역]`  
> 보관 기간 및 학습 사용: `[계약으로 확인한 조건]`  
> 동의하지 않아도 `[실제로 제공되는 비전송 기능]`을 이용할 수 있습니다.

공급자 조건이 미확인이라면 **“학습에 사용하지 않음”, “즉시 삭제”, “완전 익명”을 넣지 않습니다.**

## 3.4 서버 처리

프런트엔드 체크박스만으로 끝내지 말고, 두 API 모두 외부 호출 **전에** 검증합니다.

```json
{
  "consent": {
    "notice_version": "2026-10-26-v1",
    "purposes": ["receipt_ocr", "billing_inquiry"],
    "sensitive_data": true,
    "transfer_notice_version": "provider-v1"
  }
}
```

백엔드 권고:

- 필수 값은 실제 Boolean `true`인지 검증.
- 허용하는 고지 버전과 처리 목적 확인.
- 서버 시각과 요청 식별자 부여.
- 선택하지 않은 통증·활동량 정보는 프롬프트에서 제외.
- 공급자·처리 지역·목적이 바뀌면 동의 상태 재확인.
- 원본 이미지·건강정보를 오류 로그에 기록하지 않음.

**동의 증빙에는 현실적인 선택지가 있습니다.**

- **합성자료 해커톤:** 요청 단위 검증, 실제 환자 서비스 미출시 범위 명시.
- **실제 환자 서비스:** 최소한의 동의 증빙을 보호된 저장소에 보관. 영수증 DB나 서버 세션은 여전히 불필요합니다.

서명된 동의 토큰을 브라우저에만 보관하면 가볍지만, 사용자가 지운 뒤 사업자가 증빙을 제시하기 어렵습니다. **완전 무저장과 지속 가능한 동의 증빙을 동시에 보장한다고 설명해서는 안 됩니다.**

# 4. 질문 3 — 550B 모델 전략

## 4.1 최신 모델과 공식 심사 기준: 확인된 것과 아닌 것

코드에서 확인한 설정은 다음뿐입니다.

```python
OCR_PRIMARY = "nvidia/Nemotron-3.5-Super-VL"
OCR_FALLBACK = "Qwen/Qwen3.8-27B"
REASONING_MODEL = "nvidia/Nemotron-3-Ultra-550b-a55b"
```

이는 **문자열 설정의 존재**를 증명할 뿐입니다. 실제 모델 존재, Nebius 제공 여부, 가격, 비전 지원, 성능을 증명하지 않습니다.

사용자께서 제시한 NVIDIA 생태계·레이턴시·비용·실용성은 아래의 평가축으로 사용하되, **공식 배점이나 필수 모델 요건으로 확인한 것은 아닙니다.**

Nemotron 70B, Llama 3.1 70B/8B 역시 비교 후보로만 다룹니다. 현재 최신 권장 모델이라고 단정하지 않으며, 채택 전에 현행 카탈로그와 모델 카드를 확인해야 합니다.

## 4.2 550B가 꼭 필요한가?

**아닙니다. 현재 작업 정의에는 반드시 초대형 모델이어야 할 근거가 없습니다.**

현재 추론 작업은:

- 영수증 항목 요약.
- 문의 가능한 항목 선정.
- 불확실성 설명.
- 정중한 질의서 작성.
- 구조화된 JSON 반환.

일반 건에서는 근거가 명확한 항목과 질문 템플릿만으로도 상당 부분 처리할 수 있습니다.

중요한 점은 **통증·걸음 수만으로 치료 필요성이나 청구 부당성을 판단할 수 없다는 것**입니다. 더 큰 모델이 누락된 진료기록을 대신할 수는 없습니다.

### 550B 유지의 득실

| 평가축 | 득 | 실/한계 |
|---|---|---|
| NVIDIA 기여 | NVIDIA 모델 사용 사례가 명확함 | 더 큰 모델을 썼다는 사실만으로 기여도가 더 높아지지는 않음 |
| 품질 | 복잡한 다국어·여러 문서 종합에서 개선 가능성 | 현재 자료에서는 개선량 미측정 |
| 레이턴시 | 배포·추론 최적화에 따라 좋은 성능 가능 | 실제 p95와 서비스 안정성 미측정 |
| 비용 | 유의미한 품질 향상이 있으면 정당화 가능 | 현재 단가와 성공 건당 비용 미확인 |
| 실용성 | 예외 건 전용으로 가치 가능 | 간단한 질의서에도 기본 호출하면 과설계일 수 있음 |

또한 모델 ID의 `a55b`만 보고 활성 파라미터를 확정할 수 없습니다. 만약 MoE라면 총 파라미터와 요청당 활성 파라미터를 구분해야 합니다. **“550B라서 70B보다 무조건 느리고 비싸다” 역시 검증 없는 결론입니다.**

권고는 명확합니다.

> **550B는 기본 필수 모델이 아니라 비교·예외 처리 후보로 두십시오. 유지 여부는 실제 품질 개선으로 결정하십시오.**

## 4.3 가장 현실적인 모델 아키텍처

### 1단계: 해커톤 기본형

```text
확인된 비전 OCR 모델
         ↓
Python 파서 + 자료형/금액/국가 불확실성 검사
         ↓
검증된 NVIDIA 계열 중형 추론 모델 1회 호출
         ↓
JSON 스키마 + 항목 근거 검증
         ↓
원무과 문의 초안
```

- 현재 결정적 파서를 8B로 교체하지 않습니다.
- 숫자·금액·합계는 규칙 기반으로 처리합니다.
- 추론 모델은 항목 설명과 문장 작성에 집중합니다.
- 모델명은 실제 응답 메타데이터로 표시합니다.

### 2단계: 측정 후 경량 분기

```text
간단하고 근거 명확한 건
  → 템플릿 또는 검증된 소형 모델

복합 항목·다국어 설명이 필요한 건
  → 검증된 중형 모델

OCR 불명확·국가 불명확·합계 불일치
  → 사용자 확인 또는 재촬영
```

**OCR 오류를 큰 추론 모델로 덮지 않습니다.** “모르겠다”와 재확인이 올바른 경로인 경우가 많습니다.
